# React Frontend Implementation Plan

**Date:** 2026-03-25
**Scope:** React-based frontend consuming the Golf API, secured with Auth0

---

## Architectural Decisions

### 1. Repository Structure: Mono-repo

**Decision: Keep the frontend in the same repository as the Spring Boot API.**

Rationale:
- The `open-api.json` spec lives at the repo root (generated by `cd api && ./mvnw verify`) and can feed the TypeScript client generator directly — no cross-repo coordination needed
- A single `docker-compose.yml` at the root can orchestrate PostgreSQL, the API, and the web app together
- Atomic commits that span API changes and their corresponding UI changes
- Simpler developer onboarding — one clone, one `docker compose up`
- Small-team context: the coordination overhead of a poly-repo offers no benefit here
- CI/CD path filters are clean and non-inverted (`paths: ['api/**']` and `paths: ['web/**']`) — no exclusion rules needed
- Docker build context is set to the repo root for both services; each service's Dockerfile lives in its own subdirectory — no path hacks

Structure after implementation (**Option B — sibling directories**):
```
golf-api/                   ← GitHub repo root (rename to golf-app deferred)
├── open-api.json           ← shared contract artifact (generated by api/mvnw verify)
├── docker-compose.yml      ← full-stack orchestration
├── .github/workflows/
│   ├── api-test.yml        ← paths: ['api/**', '.github/workflows/api*.yml']
│   ├── api-release.yml     ← paths: ['api/**', '.github/workflows/api*.yml']
│   ├── web-test.yml        ← paths: ['web/**', 'open-api.json', '.github/workflows/web*.yml']
│   └── web-release.yml     ← paths: ['web/**', 'open-api.json', '.github/workflows/web*.yml']
├── api/                    ← Java/Maven project (moved from root)
│   ├── src/
│   ├── pom.xml
│   ├── mvnw
│   ├── .mvn/
│   └── Dockerfile
└── web/                    ← Next.js frontend
    ├── package.json
    ├── src/
    └── Dockerfile
```

> **What is NOT a mono-repo trade-off:**
> - Building both services on every PR — path filters prevent this entirely; if no file under `api/**` changed, the API workflow is never provisioned
> - Releasing both services on every merge — same path filter on `push` prevents double releases
> - Single shared version number — independent `tag_prefix` values (`api-v` / `web-v`) give fully separate semver streams
>
> **Genuine accepted trade-offs:**
> - 4 workflow files share checkout/Docker-setup boilerplate — reusable workflows are an option later
> - Two required PR checks instead of one — minor operational overhead (update branch protection when renaming jobs)
> - Root-level files (`docker-compose.yml`, `open-api.json`) feel unowned by either service — acceptable for a small project

> **Note:** Repo rename to `golf-app` is deferred. GitHub automatically redirects from old URLs when it happens.
>
> **Prerequisite:** This structure requires moving existing Maven project files (`src/`, `pom.xml`, `mvnw`, `.mvn/`, `Dockerfile`, `local-*` scripts) into `api/` before any frontend work begins — see **Step 0** below.

### 2. Framework: Next.js 14+ with App Router

**Decision: Next.js 14+ using the App Router (React Server Components).**

Rejected alternatives:
- **Remix**: Auth0 SDK integration is more manual; smaller ecosystem
- **Vanilla React (Vite/CRA)**: No SSR without significant additional setup — violates a hard requirement
- **React Native**: SSR is architecturally incompatible with React Native's renderer; the Expo web adapter does not produce server-rendered HTML

Next.js wins because:
- App Router's Server Components provide true SSR with zero client-side JS for data-fetching paths
- `@auth0/nextjs-auth0` v3 has first-class App Router support
- ISR (Incremental Static Regeneration) is ideal for course data that rarely changes
- API Routes serve as a BFF (Backend For Frontend) proxy, keeping access tokens off the browser
- TypeScript support is first-class, not bolted on

---

### 3. React (Web) with PWA, not React Native

**Decision: React for web. Add PWA capabilities for mobile on-course use.**

While golfers use their phones on the course, SSR is a hard requirement, and React Native's renderer cannot produce server-rendered HTML pages. Instead, configuring Next.js as a PWA (`next-pwa`) gives:
- Installable on iOS/Android home screens
- Offline caching of course data
- Native-feel navigation
- No separate codebase

### 4. TypeScript Client: Generated from OpenAPI Spec

**Decision: `@hey-api/openapi-ts` to generate a fully-typed API client from `open-api.json`.**

This generates:
- TypeScript interfaces for every schema (`ScorecardDto`, `CourseDto`, `TeeDto`, `HandicapDto`, etc.)
- Type-safe service functions for each operation (`scorecard.list`, `course.search`, etc.)
- A configured fetch client that accepts an `Authorization` header

Generation runs as an npm script (`predev` + `prebuild`) so the client is always in sync with the spec. The source spec is `open-api.json` at the repo root, which is regenerated by `cd api && ./mvnw verify`.

### 5. Frontend Unit Testing Decisions

**Three distinct layers require different strategies.**

#### 5a. UI Component Tests — Vitest + React Testing Library + MSW (browser mode)

- **Vitest**: faster than Jest, native ESM, shares Vite config
- **React Testing Library**: test through user interactions, not implementation details
- **MSW (Mock Service Worker)**: intercepts `fetch` at the network level in jsdom — catches integration bugs between component and API contract
- **`@testing-library/user-event`**: realistic event simulation (typing, clicking, tabbing)

What to test:
- Form validation paths — every Zod constraint (slope < 55, score < 1, blank required fields)
- Empty states — "no scorecards yet", "no handicap established"
- Error states — API error responses surface the right message
- Conditional UI — buttons only appear with correct scopes
- Component composition — Tee list inside Course detail renders correct data

Auth mocking: wrap components with a mock `UserProvider` injecting a fake `user` object — no real Auth0 needed.

#### 5b. API Route Handler Tests — Vitest + Node environment

Next.js Route Handlers are plain async functions accepting `Request` / returning `Response`. Testable without starting Next.js:

```ts
// src/app/api/proxy/scorecards/route.test.ts
vi.mock('@auth0/nextjs-auth0', () => ({
  getAccessToken: vi.fn().mockResolvedValue({ accessToken: 'test-token' }),
}));
```

What to test per Route Handler:
- **Happy path**: session present → Bearer token forwarded → upstream response proxied correctly
- **No session (401)**: `getAccessToken()` throws → handler returns 401 before calling Spring Boot
- **Upstream 404**: Spring Boot returns 404 → handler forwards 404 (not a 500)
- **Upstream 409**: Spring Boot returns 409 → response body is preserved
- **Upstream 500**: Spring Boot unreachable → safe error (no stack trace in body)
- **Request body passthrough**: POST/PATCH body forwarded unmodified

MSW in Node mode intercepts the handler's outbound `fetch` calls — no real API needed.

#### 5c. API Client / Service Interaction Tests — Vitest + MSW Node

Tests the generated `@hey-api/openapi-ts` client to ensure:
- `Authorization: Bearer <token>` header is present on every request
- Base URL is correctly configured from environment
- 401 → throws an identifiable error type (so callers can redirect to login)
- 404 → throws `NotFoundError`
- 409 → throws `DuplicateError`
- Network failure → throws with a useful message

Runs in the Node environment (no jsdom) — extremely fast.

### 6. End-to-End Testing Decisions

**Decision: Playwright**

Rejected alternatives:
- **Cypress**: No native multi-tab support; slower; weaker TypeScript integration
- **WebdriverIO**: More complex setup; smaller ecosystem for Next.js apps

Playwright wins because:
- Chromium, Firefox, and WebKit in one runner
- First-class TypeScript support
- `storageState` allows auth state capture and reuse (critical for avoiding Auth0 login on every test)
- `page.route()` for selective network mocking
- Parallel test execution out of the box
- Trace viewer for debugging CI failures

#### 6a. Mocking Auth0

| Option | Pros | Cons |
|---|---|---|
| **A. Real Auth0 test credentials** | Most realistic | Requires internet; flaky on rate limits |
| **B. Mock session cookie** | Fast; offline | Fake access token rejected by Spring Boot |
| **C. Test auth bypass middleware** | Fully offline | Requires env-gated code path |

**Decision: Option A (real Auth0) for E2E against the real API.**

Auth0 is only hit **once per test run** in `globalSetup`. Playwright's `storageState` reuses the session across all tests.

```ts
// playwright/global-setup.ts
export default async function globalSetup() {
  const browser = await chromium.launch();
  const page = await browser.newPage();

  await page.goto('http://localhost:3000/api/auth/login');
  await page.fill('[name=email]', process.env.E2E_USER_EMAIL!);
  await page.fill('[name=password]', process.env.E2E_USER_PASSWORD!);
  await page.click('[type=submit]');
  await page.waitForURL('**/dashboard');

  await page.context().storageState({ path: 'playwright/.auth/user.json' });
  await browser.close();
}
```

#### 6b. Seed Data and Test User Setup

**Decision: API-based seeding in Playwright `beforeAll` hooks, not SQL fixtures.**

Rationale: SQL fixtures bypass the API layer and can produce data the API would never produce. API-based seeding exercises the real write paths.

**Test isolation:** Each top-level `describe` block operates under a dedicated test user with separate Auth0 credentials:

| Test Suite | Auth0 Test User | Reason |
|---|---|---|
| Scorecards E2E | `e2e-scorecards@test.com` | Prevents handicap side-effects from other suites |
| Courses E2E | `e2e-courses@test.com` | Isolated course list |
| Handicap E2E | `e2e-handicap@test.com` | Needs exactly 20 rounds to trigger index calculation |

Each user gets a separate `storageState` file generated in `globalSetup`.

**Handicap seeding note:** Tests must seed 20 scorecards in `beforeAll` then use `expect.poll()` to wait for the async handicap calculation — mirroring the Awaitility pattern used in backend integration tests.

#### 6c. Critical E2E Flows

| Priority | Flow | Why Critical |
|---|---|---|
| P0 | Auth: Sign in → Dashboard → Sign out | Gate to everything |
| P0 | Create Scorecard → Appears in list → Handicap updates | Core workflow; async pipeline |
| P1 | Course CRUD: Create → Add Tee → Edit Course → Delete Course | Cascading tee delete |
| P1 | Course Search: results returned, blank search shows all | Key discovery feature |
| P1 | Multi-tenancy: User A cannot see User B's scorecards | Security-critical |
| P2 | Duplicate Course: 409 surfaces inline error, not crash | Common error path |
| P2 | Scorecard Delete → Handicap recalculates | Async pipeline |
| P2 | Handicap history renders chart with correct revision count | Data integrity |
| P3 | Unauthenticated access redirects to login | Middleware sanity check |
| P3 | PWA install prompt appears on supported browsers | Mobile UX gate |

### 8. CI/CD Strategy: Path-Filtered Workflows + Independent Semver

**Decision: Four workflow files with path filters; independent per-service versioning via tag prefixes.**

#### Path-filtered workflows

GitHub Actions `paths:` on `push`/`pull_request` causes the workflow to be **entirely skipped** (no runner provisioned) when no matching file changed. This is a native GitHub Actions pattern, not a mono-repo compromise.

Each workflow also includes its own workflow file in the path list to close the self-change gap — if only `.github/workflows/api-test.yml` changes, the api path filter wouldn't normally fire:

```
api workflows:  paths: ['api/**', '.github/workflows/api*.yml']
web workflows:  paths: ['web/**', 'open-api.json', '.github/workflows/web*.yml']
```

#### `open-api.json` as web workflow trigger

`open-api.json` at the repo root is the shared contract between the API and the TypeScript client. Including it in the web workflow's path filter means: whenever a spec-changing API merge lands, the web CI also runs — catching TypeScript breakage from changed schemas immediately rather than at the next dedicated web commit.

`open-api.json` must remain committed (it is consumed by the web workflow and by `npm run generate-api`). It must **not** be in `.gitignore`.

#### Independent per-service semver

`mathieudutour/github-tag-action` (already in use) supports a `tag_prefix` input. Each release workflow uses its own prefix:

| Workflow | `tag_prefix` | Resulting tag | Docker image |
|---|---|---|---|
| `api-release.yml` | `api-v` | `api-v0.0.4` | `ghcr.io/{owner}/golf-api:0.0.4` |
| `web-release.yml` | `web-v` | `web-v0.1.0` | `ghcr.io/{owner}/golf-web:0.1.0` |

The action reads only tags matching its own prefix, so the two version streams are fully independent — no new tooling required.

#### Image naming

Use `github.repository_owner` (not `github.repository`) as the image registry prefix. This avoids a `golf-api/golf-api` double-name while the repo is still named `golf-api`:

```
ghcr.io/${{ github.repository_owner }}/golf-api:${{ steps.tag.outputs.new_version }}
```

### Step 3 — Configure the API Client and BFF Proxy Layer

**Objective:** Create a server-side API client that injects the Auth0 access token into every request to the Spring Boot API.

Tasks:
- Create `web/src/lib/api/client.ts` (server-only module):
  ```ts
  import { createClient } from './generated/client';

  export function getApiClient(accessToken: string) {
    return createClient({
      baseUrl: process.env.API_BASE_URL,
      headers: { Authorization: `Bearer ${accessToken}` },
    });
  }
  ```
- Create `web/src/lib/api/server.ts`:
  ```ts
  import { getAccessToken } from '@auth0/nextjs-auth0';
  import { getApiClient } from './client';

  export async function getAuthedApiClient() {
    const { accessToken } = await getAccessToken();
    return getApiClient(accessToken!);
  }
  ```
- Add `server-only` package to prevent accidental client-side import
- Set env vars: `API_BASE_URL=http://localhost:8080` (dev), `http://api:8080` (Docker)
- Create Next.js Route Handlers under `web/src/app/api/proxy/` for client-side mutations:
  1. Validate session cookie present
  2. Exchange for access token via `getAccessToken()`
  3. Forward request to Spring Boot with Bearer token
  4. Return response

Deliverables:
- Server Components can call `getAuthedApiClient()` and get typed results
- Route Handlers exist for each mutation operation
- No access token ever serialized to the browser

## Technical Notes

### OpenAPI Client Regeneration
`open-api.json` is generated by `cd api && ./mvnw verify` — the `springdoc-openapi-maven-plugin` is configured to write output to `${project.basedir}/..` (repo root). The frontend's `predev`/`prebuild` scripts in `web/package.json` consume `../open-api.json` (one level up from `web/`). If the spec changes, the TypeScript compiler will surface any breakage in calling code immediately.

### Auth0 Token Scopes
`AUTH0_SCOPE` must include all required scopes:
```
openid profile email read:scorecard write:scorecard read:course write:course read:handicap
```

### BFF Proxy Pattern
- Server Components: call Spring Boot directly (server-to-server, token in memory)
- Client Components: call Next.js Route Handlers → Spring Boot (token never sent to browser)

### SSR Cache Strategy
- Course list: `revalidate: 3600` (ISR — changes infrequently)
- Scorecard list: no cache — user data changes frequently
- Dashboard: no cache — stale handicap data would be confusing
- Handicap history chart: Server Component fetches, passes props to Client Component for rendering

### Scorecard UX Enhancement
`ScorecardRequestDto` takes `courseName` and `teeName` as plain strings. Consider adding an autocomplete that calls `GET /v1/course/search` as the user types, then auto-populates `teeName`, `par`, `rating`, and `slope` from the selected tee — significantly improves UX for repeat courses.
